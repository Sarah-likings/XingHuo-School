## 1. 总则

### 1.1 架构基线

- **前后端分离的单体架构**：一个 Next.js 工程（学生端 + 管理端路由）+ 一个 FastAPI 服务；
- **不引入**消息队列、微服务、Kubernetes、GraphQL、服务网格；
- **一份 `docker-compose.yml` 起全栈**，任何人 clone 后 30 分钟内可跑通（门禁 G2）；
- 端到端只有两种协议：**HTTP/REST（JSON）** 与 **WebSocket**。

### 1.2 版本基线（冻结，不随大版本升级）

| 组件 | 版本 | 组件 | 版本 |
| --- | --- | --- | --- |
| Node.js | 20 LTS | Python | 3.12 |
| Next.js | 14 | FastAPI | 最新稳定版 |
| TypeScript | 5.x（`strict: true`） | SQLAlchemy | 2.x |
| Tailwind CSS | 3.x | Alembic | 最新稳定版 |
| PostgreSQL | 16 | Redis | 7 |
| Docker / Compose | 24.x / v2 | Nginx | 1.24 |

### 1.3 模块边界（不要跨模块改别人负责的域）

| 域 | 后端目录 | 前端目录 | 负责人 |
| --- | --- | --- | --- |
| 认证与实名 | `services/auth`、`services/verify` | `features/auth` | 吕振楠（后端）/ 付苏琪（前端） |
| 任务与检索 | `services/task` | `features/task` | 吕振楠 / 付苏琪 |
| 订单与状态机 | `services/order` | `features/order` | 吕振楠 |
| 担保交易 | `services/wallet` | `features/wallet` | 吕振楠 |
| 私聊与消息 | `services/chat` | `features/chat` | 吕振楠 / 付苏琪 |
| 评价与信用 | `services/review` | `features/review` | 吕振楠 |
| 生活帖与举报 | `services/post`、`services/report` | `features/post` | 付苏琪 |
| 后台管理 | `services/admin`、`routers/admin` | `features/admin` | 付苏琪 / 刘静怡 |

跨域改动（例如订单要读钱包的余额）**通过 service 方法调用**，不允许跨模块直接操作对方的表。

## 2. 前后端协作契约

### 2.1 接口先行

1. 后端先提交带 OpenAPI 注解的 `routers/*.py`，Swagger 自动生成契约；
2. 前端从 `/openapi.json` 生成类型（`openapi-typescript`），**不手写接口类型**；
3. 契约变更必须同步：接口有增删改，PR 描述必须写“接口变更”一节，并知会前端。

### 2.2 统一响应结构

```json
{ "code": "OK", "msg": "成功", "data": { } }
```

- `code`：字符串枚举，见 [2.3 错误码](#23-错误码)；成功统一 `OK`；
- `msg`：给人看的中文提示，**不带堆栈、不带 SQL、不带内部路径**；
- `data`：业务数据；列表统一 `{ "items": [], "page": 1, "page_size": 20, "total": 128 }`。

HTTP 状态码承担语义，`code` 承担细分原因；**不允许全部返回 200 再靠 code 区分失败**。

### 2.3 错误码

| HTTP | code | 触发场景 | 前端必须做的事 |
| --- | --- | --- | --- |
| 400 | `BAD_REQUEST` | 参数缺失/格式错误 | 提示重试并记录 trace_id |
| 401 | `UNAUTHORIZED` | 未登录、令牌过期或无效 | 清登录态 → 跳登录 → 回跳原页面 |
| 402 | `INSUFFICIENT_BALANCE` | 可用余额不足冻结/打款 | 提示"余额不足"，引导联系管理员充值 |
| 403 | `FORBIDDEN` | 越权（操作他人订单、非会话成员） | 提示无权限，不暴露资源是否存在 |
| 403 | `NOT_VERIFIED` | 未实名却调用发布/接单 | 弹实名认证引导，带跳转 |
| 404 | `NOT_FOUND` | 资源不存在或已下架 | 展示"已下架/已删除"空态 |
| 409 | `CONFLICT` | 状态冲突（非法状态迁移） | 刷新详情后重新判断可操作项 |
| 409 | `TASK_TAKEN` | 抢单失败（已被他人抢走） | 提示并回到大厅/刷新 |
| 409 | `DUPLICATE` | 重复申请、重复评价、重复审核 | 提示"已提交过"并展示已有记录 |
| 422 | `VALIDATION_FAILED` | 字段校验失败、命中违规词 | 高亮字段 + 说明命中规则 |
| 429 | `TOO_MANY_REQUESTS` | 限流、申请人数已满 | 提示稍后重试或换任务 |
| 500 | `INTERNAL_ERROR` | 服务异常 | 提示稍后再试，展示 trace_id |

### 2.4 命名与格式

| 项目 | 约定 |
| --- | --- |
| JSON 字段 | `snake_case`（与数据库列名一致，减少映射） |
| 金额 | **字符串**，两位小数，如 `"20.00"`；单位元；前端不做浮点运算 |
| 时间 | ISO 8601 带时区，如 `2026-11-10T12:00:00+08:00`；展示到分钟 |
| 枚举 | 大写下划线，如 `ASSIGNED`、`OPEN`；前端展示用中文映射表 |
| ID | 数值自增或 UUID 二选一（**全库统一为数值自增**，对外不暴露业务含义） |
| 布尔 | `true/false`，不用 0/1 |
| 空值 | 未赋值的可选字段返回 `null`，不返回空字符串 |

### 2.5 幂等

- 写接口凡可能被重复触发的（选定接单人、验收、打款、退款），必须支持幂等键：请求头 `Idempotency-Key`（前端生成 UUID），服务端 24 小时内同键返回首次结果；
- 定时任务天然要求幂等，见 [4.10](#410-定时任务)。

## 3. 前端技术要求

### 3.1 工程结构与依赖方向

```text
apps/web/
├── app/                     # App Router：路由与页面（不含业务逻辑）
│   ├── (student)/           # 学生端路由组
│   ├── admin/               # 管理端路由组
│   └── api/                 # 仅必要的 BFF 转发（默认不用）
├── components/ui/           # 无业务语义的原子组件（Button/Input/Modal/Toast）
├── components/business/     # 有业务语义的复用组件（TaskCard/OrderStatusBar）
├── features/<domain>/       # 域内组件、hooks、api 封装
├── lib/                     # fetcher / ws / auth / formatter / constants
├── types/                   # 由 OpenAPI 生成的类型（不手改）
└── styles/                  # 全局样式与设计令牌
```

**依赖方向**：`app → features → components → lib`。禁止反向依赖（`lib` 不许 import `features`），禁止 `features/a` 直接 import `features/b` 的内部文件。

### 3.2 语言与类型

- `tsconfig.json` 必须 `"strict": true`；
- **禁止 `any`**；确实未知用 `unknown` 并收窄；第三方库缺类型用 `declare module` 补齐；
- 接口类型来自 `types/api.ts`（OpenAPI 生成），页面不重新定义；
- 状态枚举从 `lib/constants.ts` 导入，**禁止在页面里写字面量** `"ASSIGNED"`。

### 3.3 组件与样式

- 样式只用 **Tailwind 工具类 + 设计令牌**，禁止行内 `style`（动态定位除外）；
- 设计令牌集中在 `tailwind.config.ts`：主色 `brand`、状态色 `state-*`（open/assigned/delivered/completed/cancelled/appealing/refunded）、语义色 `danger/success/warning`；
- 同一视觉元素（卡片、状态徽标、金额文本）**只有一个组件**，不允许各页面各写一份；
- 金额显示统一组件 `<Money value="20.00" />`（固定两位小数 + 单位），时间统一 `<Time />`（相对时间 + title 显示绝对时间）。

### 3.4 路由与数据获取

| 场景 | 做法 |
| --- | --- |
| 首屏列表/详情 | **Server Component** 直出（`fetch` 带 `revalidate`），保证首屏可交互 ≤ 2.5 s |
| 交互后刷新 | 客户端调用同一套 `fetcher`，成功后 `router.refresh()` 或局部状态更新 |
| 加载态 | `loading.tsx` + 骨架屏；禁止整页白屏转圈 |
| 缓存 | 大厅列表 `revalidate: 30`；钱包、订单详情 `no-store` |
| 鉴权 | 令牌存 **httpOnly Cookie**（前端不读 token）；401 统一拦截 |

`lib/fetcher.ts` 是唯一出口：自动附带凭据、统一解析 `{code,msg,data}`、统一抛 `ApiError(code,msg,traceId)`、401 跳登录。

### 3.5 状态管理

优先级：**URL > 服务端数据 > 本地组件状态 > 全局 store**。

- 筛选、排序、分页、Tab 一律放 **URL 查询参数**（可分享、可回退、可刷新）；
- 服务端数据不进全局 store（避免双份真相）；
- 全局 store 只放**会话级**内容：当前用户、未读消息数、Toast 队列；用 Zustand，禁止引入 Redux；
- 表单草稿存 `sessionStorage`（发布任务防误关），提交成功后清除。

### 3.6 表单与校验

- 统一 React Hook Form + Zod；
- Zod schema 与后端字段规则逐条对齐（长度、范围、必填），**前端校验只为体验，服务端结果为最终结果**；
- 提交按钮进入 loading 后必须禁用，防重复提交；失败后恢复并保留用户输入；
- 422 返回的字段错误必须**回填到对应输入框**，不允许只弹 Toast。

### 3.7 实时消息

```text
单例连接（lib/ws.ts）
├── 建连：携带 Cookie 鉴权，URL /ws/chat/{sessionId}
├── 心跳：30 s 一次 ping，连续 2 次无 pong 判定断线
├── 重连：指数退避 1s → 2s → 4s → 8s（上限 30s），重连成功后按会话补拉未读
├── 页面切换：不重建连接（同一会话复用）
└── 卸载：组件卸载只关闭订阅，连接由 App 级 Provider 管理
```

- 消息以**服务端为准**：本地乐观插入的消息带临时 id，收到推送后用 `msg_id` 替换；
- 未读数变化必须同步到全局 store 与页面标题。

### 3.8 状态机 → 交互映射

> 这是"状态机只写一次，前端不再各写 if"的落地方式。**必须查表实现**：`features/order/actions.ts` 导出 `getActions(status, role, order)`，页面只渲染返回值。

| 订单状态 | 雇主可操作 | 接单者可操作 | 其他角色的按钮 |
| --- | --- | --- | --- |
| `OPEN` 待接单 | 查看申请、选定接单人、取消任务 | 申请接单 | 只读；按钮置灰并提示"仅雇主可操作" |
| `ASSIGNED` 已选定 | 查看进度、催办、申诉 | 上传凭证交付、申诉 | 申请按钮置灰提示"该任务已被接走" |
| `DELIVERED` 已交付 | 验收通过、拒收、申诉 | 仅查看（等待验收） | 只读 |
| `COMPLETED` 已完成 | 评价（7 天内）、查看凭证 | 评价、查看收入 | 只读 |
| `APPEALING` 申诉中 | 补充证据、等待裁决 | 补充证据、等待裁决 | 只读，提示"仲裁中，48～72 小时出结果" |
| `CANCELLED` 已取消 | 只读 | 只读 | 只读 |
| `REFUNDED` 已退款 | 只读、查看退款流水 | 只读 | 只读 |

要求：**按钮的“禁用 + 原因”必须成对出现**，不允许只把按钮藏起来（用户会以为功能没做）。

### 3.9 错误与空态

每个列表/详情页必须实现四种状态：**加载（骨架屏）、空态（说明 + 下一步按钮）、错误（原因 + 重试）、无权限（说明 + 申请入口）**。

错误文案模板：`发生了什么` + `为什么` + `怎么办`，例如：

- 403 `NOT_VERIFIED` → "发布任务需要先完成实名认证（约 1 分钟）。去认证"
- 409 `TASK_TAKEN` → "该任务刚刚被其他同学接走了。看看其他任务"

### 3.10 移动端适配

- 断点：`sm 640 / md 768 / lg 1024`；学生端按 **移动优先** 设计，管理端按桌面优先；
- 触控目标 ≥ 44×44 px；主要操作按钮位于拇指可达区（屏幕下半部）；
- 处理 `safe-area-inset`、输入法遮挡（表单页可滚动）、`100vh` 在移动端浏览器的兼容；
- 图片上传前压缩到长边 1600 px、≤ 800 KB。

### 3.11 性能预算

| 指标 | 预算 | 验证方式 |
| --- | --- | --- |
| 首屏可交互（LCP/TTI） | ≤ 2.5 s（4G、中端机） | Lighthouse 移动端 |
| 首屏 JS（gzip） | ≤ 200 KB | `next build` 输出 |
| 图片 | 统一 WebP/AVIF + 懒加载 | 构建产物检查 |
| 列表 | 分页 20 条/页，禁止一次拉全量 | 接口参数检查 |
| 管理端代码 | 不得进入学生端首屏包 | 构建分析 |

### 3.12 可访问性与文案

- 图文对比度 ≥ 4.5:1；键盘可完成主要流程（发布 → 申请 → 交付 → 验收）；
- 图标按钮必须带 `aria-label`；表单 `label` 与输入框关联；
- 中文文案统一规范：术语用“任务 / 订单 / 接单人 / 悬赏”，不出现中英混排的“Task”；
- 金额一律“¥20.00”样式；时间一律“11-10 12:00”样式。

### 3.13 代码风格与检查

- ESLint（`next/core-web-vitals` + `@typescript-eslint`）+ Prettier；
- husky `pre-commit`：`lint-staged` 跑 ESLint + `tsc --noEmit`；
- commitlint 校验提交信息符合 Conventional Commits；
- 组件文件 ≤ 300 行，超出即拆分；单文件导出多个组件时按“一文件一主组件”组织。

## 4. 后端技术要求

### 4.1 分层与依赖方向

```text
routers/      路由层：解析请求、调用 service、返回统一响应（不写业务）
   ↓
services/     业务层：业务规则、事务边界、状态机、外部能力调用
   ↓
repositories/ 数据访问层：只做增删改查与查询组装（不写业务分支）
   ↓
models/       ORM 模型（表结构）
schemas/      出入参校验（Pydantic）
```

**禁令**：router 里不出现 SQL 与业务分支；repository 里不出现业务规则；service 之间可以互相调用，但**不允许循环依赖**。

### 4.2 命名与目录

| 项目 | 约定 |
| --- | --- |
| 模块文件 | 小写下划线：`order_service.py`、`wallet_repository.py` |
| 类 | 大驼峰：`OrderService`、`WalletRepository` |
| 函数/变量 | 小写下划线；布尔用 `is_/has_/can_` |
| 路由前缀 | `/api/<域>`，如 `/api/tasks`、`/api/orders`、`/api/admin` |
| 事务函数 | 以 `_tx` 结尾或在 service 内显式 `with session.begin()` |

### 4.3 鉴权与权限

- JWT 存 httpOnly Cookie，claims 至少包含：`sub`（user_id）、`role`（student/admin）、`verified`（是否实名）、`exp`；
- **401 与 403 严格区分**：未登录=401；已登录但无权限=403（`FORBIDDEN` / `NOT_VERIFIED`）；
- 每个写接口必须做**资源归属校验**（是否本人订单、是否会话成员、是否该任务雇主），不允许只校验登录；
- 管理员**不可参与交易**（不可发布、接单、评价）；管理员访问学生端交易接口一律 403；
- 限流：单 IP 60 次/分钟；发布任务 10 次/小时/用户；登录失败 5 次锁定 15 分钟。

### 4.4 订单状态机

**唯一入口**（其他任何位置禁止 `UPDATE orders SET status=...`）：

```python
# services/order_service.py（规范示例）
ALLOWED: dict[str, set[str]] = {
    "OPEN":       {"ASSIGNED", "CANCELLED"},
    "ASSIGNED":   {"DELIVERED", "OPEN", "APPEALING"},
    "DELIVERED":  {"COMPLETED", "APPEALING"},
    "APPEALING":  {"COMPLETED", "REFUNDED"},
    "CANCELLED":  {"REFUNDED"},
    "COMPLETED":  set(),
    "REFUNDED":   set(),
}

def transition(order_id: int, frm: str, to: str, operator: int, remark: str = "") -> None:
    """状态迁移：校验合法性 + 条件更新 + 写 order_event，三件事在同一事务内。"""
    if to not in ALLOWED[frm]:
        raise ConflictError("CONFLICT", f"不允许从 {frm} 迁移到 {to}")
    rows = order_repo.cas_status(order_id, frm, to)      # 条件更新，见 4.6
    if rows != 1:
        raise ConflictError("CONFLICT", "订单状态已变化，请刷新")
    order_repo.add_event(order_id, frm, to, operator, remark)
```

- 每条迁移必须写 `order_event`（原状态、新状态、操作人、时间、备注）——这是履约证据链；
- 超时迁移由定时任务发起，必须幂等（同一订单重复触发不产生第二次迁移）；
- 状态枚举与 `ALLOWED` 表**只在后端定一处**，前端通过接口或常量文件派生。

### 4.5 资金与事务

| 规则 | 说明 |
| --- | --- |
| 金额类型 | Python `Decimal`，DB `DECIMAL(10,2)`；**禁止 float**；序列化为字符串 |
| 双账 | `wallet.available` 与 `wallet.frozen` 两列；`available >= 0` 由 CHECK 约束 + 条件更新双重保证 |
| 冻结 | `UPDATE wallet SET available = available - :amt, frozen = frozen + :amt WHERE user_id = :uid AND available >= :amt` |
| 打款 | 同一事务内：冻结减、接单者可用加、写 `SETTLE` 流水、订单置 `COMPLETED` |
| 退款 | 同一事务内：冻结减、雇主可用加、写 `REFUND` 流水、订单置 `REFUNDED` |
| 流水 | `fund_flow` **只增不改不删**，必须写 `balance_after` 便于核对 |
| 对账 | 每日 03:30 校验 `Σ可用 + Σ冻结 = Σ流水累计净额`；不平即置全站只读并告警 |
| 禁止 | 禁止“先查余额再扣减”；禁止在事务外发通知（通知失败不应回滚资金） |

### 4.6 并发控制

**抢单/选定接单人**必须用条件更新（CAS），以影响行数判定胜负：

```sql
UPDATE orders
   SET status = 'ASSIGNED', taker_id = :uid, assigned_at = now()
 WHERE id = :oid AND status = 'OPEN';
```

- 影响行数 = 1 → 胜出，继续冻结资金；= 0 → 立即返回 409 `TASK_TAKEN`；
- 兜底：`UNIQUE(task_id)` 与状态枚举约束，防止代码写错产生双主；
- **禁止** `SELECT ... 然后 if 判断 ... 再 UPDATE` 的模式；
- 需要重试的场景（乐观锁版本号冲突）最多重试 2 次并加随机抖动，仍失败返回 409；
- 必须有并发测试：50 线程并发同一订单，成功数**恰好为 1**。

### 4.7 数据访问与建模

| 规则 | 说明 |
| --- | --- |
| 表名/列名 | 小写下划线，单数表名（`task`、`order`、`fund_flow`） |
| 审计字段 | 所有业务表含 `created_at`、`updated_at`；资金与事件表 `created_at` 只增 |
| 逻辑删除 | 除流水/事件/审计外统一 `deleted_at`；查询必须带 `deleted_at IS NULL` |
| 索引 | 外键列必须有索引；高频查询按 `(user_id, created_at)`、`(status, deadline)` 建联合索引 |
| 迁移 | 只用 Alembic 生成，禁止手改线上表结构；迁移脚本必须可回滚 |
| SQL | 一律 ORM 或参数化 SQL；**禁止字符串拼接**；复杂报表查询需评审 |
| 枚举 | 状态字段用 `VARCHAR + CHECK`（不用 PG enum，便于扩展） |
| 敏感字段 | 学号、姓名、影像对象键按 3.6.1 节处理：最小采集、加密存储、脱敏展示 |

### 4.8 接口实现规范

- 出入参用 Pydantic schema，**不复用 ORM 模型当 schema**；
- 列表接口统一分页参数 `page`、`page_size`（默认 20，上限 100）；
- 写接口返回变更后的关键字段（前端据此局部更新，避免再请求一次）；
- 每个 router 写 `summary` 与 `response_model`，保证 Swagger 可读；
- 幂等要求见 [2.5](#25-幂等)；
- 文件上传接口必须限制类型（JPG/PNG）与大小（≤5 MB），并校验可解码。

### 4.9 实时消息

- 建连时校验 JWT 与会话归属（非会话成员一律 403 并断开）；
- **先落库再推送**：`INSERT message` 成功后才 `push`，保证"推出去的必已持久化"；
- 推送失败不影响落库；离线用户登录后按会话拉取未读；
- 连接管理用 Redis 记录在线状态（`ws:online:{user_id}`，TTL 60 s 心跳续期）；
- 单任务私聊人数上限 5 人（申请人数上限的连带约束）。

### 4.10 定时任务

| 任务 | 频率 | 幂等键 | 失败处理 |
| --- | --- | --- | --- |
| 超时关单 / 自动完成 | 每分钟 | `order_id` + 目标状态 | 记录失败并重试下一轮 |
| 资金对账 | 每日 03:30 | 当日日期 | 不平即置全站只读并告警 |
| 全量备份 | 每日 03:00 | 当日日期 | 失败告警，保留上一份可用备份 |
| 备份清理 | 每日 03:40 | 当日日期 | 保留 7 天 |

要求：所有任务**可手工触发**（后台按钮或管理命令）、**可补跑**、**有执行日志**；超时阈值（48 小时、72 小时）为配置项，不写死。

### 4.11 日志、审计与脱敏

- 结构化日志（JSON）：`time`、`level`、`trace_id`、`user_id`、`path`、`code`、`duration_ms`；
- 请求入口生成 `trace_id` 并透传到响应头 `X-Trace-Id`，500 时返回给前端便于排查；
- **脱敏清单**（日志与异常信息里一律不得出现）：密码、JWT、学号全量、姓名、学生证影像 URL/对象键、完整手机号；
- `audit_log` 记录：`actor_id`、`action`、`target_type`、`target_id`、`detail`、`created_at`，覆盖审核、查看影像、下架、封禁、仲裁、导出、资金操作。

### 4.12 异常处理

- 定义统一异常基类 `AppError(code, msg, http_status)`，全局异常处理器转成统一响应；
- **禁止吞异常**（`except: pass`）；捕获后要么转业务异常，要么记录并重新抛出；
- 数据库异常统一转 500，**不向客户端暴露堆栈**；
- 每个请求一个事务边界：service 抛异常则整体回滚，不允许“部分成功”的写操作。

### 4.13 测试要求

| 层级 | 范围 | 通过标准 |
| --- | --- | --- |
| 单元测试 | 状态机迁移、金额计算、权限判定、对账公式 | 覆盖率 ≥ 70%，全绿 |
| 接口测试 | 16 个 REST + 1 个 WS，正常与异常分支 | 分支全覆盖（401/403/409/422/429） |
| 集成测试 | 前端调用链、冻结→验收→打款 | 主链路 + 3 条异常分支全通 |
| 并发测试 | 50 线程抢同一订单 | 成功数恒为 1，其余 409 |
| 端到端 | 5 条主链路 | Playwright 全绿 |
| 性能 | 大厅列表、抢单接口 | P95 达标（800 ms / 300 ms） |

测试数据与生产库**完全隔离**；涉及资金的用例必须用独立数据库实例或事务回滚。

### 4.14 性能与安全

**性能**

- 列表查询必须命中索引，禁止 N+1（用 `selectinload` 或显式 join）；
- 热数据（任务大厅首页）可缓存 Redis 30 秒，写操作后失效；
- 单接口 SQL 执行 ≤ 100 ms（本地），慢查询必须记录 `>200 ms` 并打印 SQL；
- 分页必须带 `LIMIT`，禁止全表扫描到内存再切片。

**安全**

- 全站 HTTPS；Cookie `Secure` + `SameSite=Lax` + `HttpOnly`；
- 防注入（ORM/参数化）、防 XSS（前端转义 + 富文本白名单）、防 CSRF（SameSite + 写接口校验 Origin）、防重放（幂等键）；
- 越权防护：每个资源访问都校验归属（AT-13）；
- 学生证影像：加密存储、签名 URL 5 分钟有效、每次查看写审计；
- 依赖安全：新增依赖须说明用途，禁止引入无维护的包。

## 5. 数据与一致性

### 5.1 枚举单一来源

订单状态、任务分类、错误码在仓库内**只有一处定义**：

```text
apps/api/app/core/enums.py     ← 后端权威定义（状态、分类、错误码）
apps/web/lib/constants.ts      ← 由后端导出/生成，禁止手写第二份
```

前端出现任何状态字面量（如 `if (status === "ASSIGNED")`）都视为**缺陷**。

### 5.2 对账与补偿

- 对账恒等式：`Σ wallet.available + Σ wallet.frozen = Σ fund_flow 净额`；
- 不平的处理顺序：**置全站只读 → 导出差异明细 → 人工核对 → 解冻并记录原因**；
- 所有资金动作必须能在 `fund_flow` 中找到对应记录；找不到即为缺陷（P0）。

### 5.3 备份与恢复

- 数据库每日 03:00 全量备份，保留 7 天，备份文件投递到对象存储独立目录；
- 恢复演练：至少一次“用备份恢复到新实例”的验证，并记录耗时；
- 关键操作（结算、退款、对账）必须有回滚预案说明。
